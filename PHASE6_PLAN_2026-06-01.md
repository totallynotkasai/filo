# Filo — Phase 6 Architectural Refactor & Audit-3 Remediation Plan (2026-06-01)

Third audit cluster: a 9-agent adversarial sweep (6 finders + 3 verifiers) over
the post-Audit2 working tree, focused on **data integrity** and **concurrency /
lifecycle / error handling**. **77 candidates raised, 68 confirmed/partial, 8
refuted, 11 new bugs discovered by the verifiers themselves during refutation.**
Total agent budget: 9 (well under the audit's 10-agent cap).

> **Headline (read once, then operate by it).** The infrastructure layer
> (`atomicWriteFile`, the 25-gate CI ratchet suite, the schema-driven IPC
> envelope, the command snapshot discipline) is genuinely 8-9/10 and was
> correctly assessed by the earlier audits. **But every Audit2 fix-X-instance
> plan has since produced a matching fix-Y-instance gap**: 2.4 fixed
> `UpdateBoardSettingsCommand` but not `UpdatePropertiesCommand` /
> `UpdateOrphanFrontmatterCommand` / `UpdateTaskFieldCommand`; 5.6 fixed
> `TaskListBoard`'s timer but not `KanbanBoard`'s; the 4.8 source-preserving FM
> engine is bypassed by `sync-frontmatter`; 5.4 / 5.5 platform-blind validators
> block every POSIX vault. **The problem is not bugs; it is the absence of
> structural invariants that prevent bug *classes*.** Phases 6.1 R1-R5 are
> those invariants. The rest of the plan is residual content that shrinks as
> the refactors land.

---

## Strategy & sequencing (read this first)

**This plan is deliberately not another fix-list.** Two-thirds of the audit
cluster across five seams where peer modules share a bug shape and the prior
audits caught some instances but not all. We close each class with **one
chokepoint + one CI gate** so future code cannot reopen the seam — the same
pattern that took `ci:verify` from 7 gates to 25, applied to the next 5
invariants.

- **Phase 6.0 (criticals)** lands first. Each is one small commit, blocks
  dogfooding, and has no design tradeoff. **3 items, S each.**
- **Phase 6.1 (refactors)** lands next. Every later phase shrinks once the
  corresponding class is dead. R1, R3, R5 are S; R2, R4 are M. **~5-8 working
  days total.** Each refactor ships **with its CI gate added to `ci:verify` in
  the same commit** — without the gate, the seam reopens within one feature
  commit.
- **Phase 6.2 (residual high)** is what's left after the refactors absorb
  their class. Re-grep before each — line numbers will drift and several items
  collapse when their class dies.
- **Phase 6.3 (Phase-5 regressions)** is "undo last week's mistakes" — silent
  regressions the hygiene batch shipped: POSIX vault unusable, baseline not
  seeded for `.filo/` configs, dead-storage growth, line-ending churn.
- **Phase 6.4 (medium/low backlog)** is everything else — defer until 6.0-6.3
  land, then re-prioritise from real dogfood data.

**Stopping rule** (definition of done for "I can trust my notes"). **Phases
6.0 + 6.1 + 6.3 land** + `ci:verify` green + an independent vault backup
exists. Stop broad auditing; start dogfooding. Phase 6.2 trickles in during
dogfooding, prioritised by which seams you hit first.

## Discipline for every item

1. Write the regression test, **watch it fail** (especially 🔍 items).
2. Fix the smallest thing that makes it pass.
3. For each refactor (6.1.R*), **the CI gate ships in the same commit** as
   the chokepoint. The gate going green on the new code is the load-bearing
   contract; without it the seam reopens within one feature commit.
4. `npm run ci:verify` green end-to-end.
5. One commit per item where practical; reference the ID (e.g. `6.0.C2`,
   `6.1.R2`) in the message.

## Legend

- **Severity:** 🔴 Critical · 🟠 High · 🟡 Medium · 🟢 Low
- **Confidence:** ✅ confirmed by adversarial reviewer · 🔍 likely (reproduce with a failing test FIRST — if you can't, downgrade to a doc note)
- 💾 = can lose / corrupt / desync user data
- **Effort:** S ≈ <½ day · M ≈ ½-2 days · L ≈ 2+ days
- **Class-kill** = a structural refactor that closes a bug *class* via invariant + CI gate, not a one-off fix

# PHASE 6.0 — 🔴 Criticals (must land before dogfooding)

### 6.0.C1 — `openVault()` never closes the previous vault → every user-driven vault switch fails 🔴 ✅ 💾

- **Where:** [vault.svelte.ts:806-899](src/renderer/stores/vault.svelte.ts:806) (`openVault`), [vault.svelte.ts:946](src/renderer/stores/vault.svelte.ts:946) (only `vault:close` call site, inside `closeVault`), [vaultCandidate.ts:149](src/renderer/lib/vault/vaultCandidate.ts:149) (`loadVaultCandidate` → `vault:init-config`), [board.ipc.ts:108-113](src/main/ipc/board.ipc.ts:108) (main-side guard that throws on stale registry).
- **Mechanism:** `openVault('B')` fires `fireVaultSwap('pre-swap')` and then `loadVaultCandidate('B')` — **but never invokes `'vault:close'`**. `init-config` then runs on the main side, reads `current = vaultRegistry.currentVaultPath` (still vault A), evaluates `!isActiveVault(B)` (true), and throws `'A different vault is already active'`. The renderer shows "Failed to open vault" and the user is stuck. Straggler timers from A continue firing against A's registry; the renderer believes it is mid-transition; `vaultStore.path` returns `''`.
- **Fix:** Inside `openVault`, after the `'pre-swap'` dispatch but before `loadVaultCandidate`, when a previous vault exists, `await window.filo.invoke('vault:close')` (or a renderer-side `closeActiveVaultOnMain()` helper that does the same). This mirrors `closeVault`'s main-side teardown so `init-config(B)` sees a cleared registry.
- **Test:** integration — open vault A, call `openVault(B)` with a fixture, assert `init-config(B)` does not throw and `vaultStore.path === B`. Add an `ipc:vault-init-config-on-empty-registry` invariant assertion.

### 6.0.C2 — `applyReloadFromDisk` doesn't cancel pending writes → Reload silently becomes Keep-local 🔴 ✅ 💾

- **Where:** [document.svelte.ts:729-753](src/renderer/stores/document.svelte.ts:729) (`applyReloadFromDisk`), [markdownFileWriter.ts:493-498](src/renderer/lib/vault/markdownFileWriter.ts:493) (gateway closure capture), [markdownFileWriter.ts:719](src/renderer/lib/vault/markdownFileWriter.ts:719) (the existing `cancelMarkdownWritesForDocument` helper). **Call sites that all hit this bug:** `promptModifiedFile`, `promptPropertiesPopupModified`, `promptMarkdownPendingWriteConflict`, the bulk Reload-all branch, `promptPartialReadExhausted`, `promptExternalEditOnSync`, `promptReloadRecoveryIfSuspicious` (7 total, all in [vaultExternalChanges.ts](src/renderer/stores/vaultExternalChanges.ts)).
- **Mechanism:** `applyReloadFromDisk` replaces body+frontmatter and clears `dirtyWriters` but never calls `cancelMarkdownWritesForDocument(docId)`. The gateway's `scheduleMarkdownWrite` captured `args.body` by closure at *schedule* time (`() => args`); `writeMarkdownFile` then reads frontmatter live (`getFrontmatter(docId)` → post-Reload FM) but `body` from the frozen snapshot (pre-Reload typed body). ~250 ms after Reload the timer fires `{post-Reload FM, pre-Reload body}` to disk, silently inverting the Reload and clobbering the external edit. The post-write `noteBaseline` re-stamps the now-clobbered state as canonical, masking the drift on subsequent checks.
- **Fix:** Closed structurally in **6.1.R1**. For this phase 6.0 commit, the minimum is: call `cancelMarkdownWritesForDocument(docId)` *as the first line* of `applyReloadFromDisk` (before `replaceState`/`updateContent`). Also `await flushAllPendingFrontmatterWrites()` for the same docId in case a frontmatter scheduler entry is also armed.
- **Test:** open `Notes.md` in `DocumentEditor`, type 5 chars, fake an external write + classifier event that fires Reload, advance fake timers by 400 ms, assert disk content equals the post-Reload bytes and the editor's pre-Reload body did **not** land.

### 6.0.C3 — `handleExternalChange` body-only reload-silently — same primitive as C2, listed for verification 🔴 ✅ 💾

- **Where:** [document.svelte.ts:684-687](src/renderer/stores/document.svelte.ts:684) (clean-editor reload-silently path), [markdownFileWriter.ts:397-415](src/renderer/lib/vault/markdownFileWriter.ts:397) (stale-cache re-read branch — not triggered, so doesn't protect).
- **Mechanism:** Identical to 6.0.C2 — the audit surfaced it as a separate finding to make clear the bug is **not** gated by frontmatter sync. A body-only edit followed by external reload-silently still hits the closure-captured pre-Reload `args.body`.
- **Fix:** Subsumed by 6.0.C2 once `applyReloadFromDisk` self-cancels. Adding this as a separate item so the regression test exercises the body-only path explicitly.
- **Test:** body-only edit + external reload-silently classifier event → no body-clobber on disk.

# PHASE 6.1 — 🟠 Structural refactors that kill bug classes (class-kill)

Each item is **one chokepoint + one CI gate added to `ci:verify`**, shipped in
the same commit. The gate is the load-bearing contract — without it, the next
feature commit reopens the seam.

### 6.1.R1 — `applyReloadFromDisk` self-cancels gateway writes (class-kill: "Reload silently overwrites") 🟠 ✅ 💾 S

- **Where:** [document.svelte.ts:729-753](src/renderer/stores/document.svelte.ts:729). Callers: 7 sites in [vaultExternalChanges.ts](src/renderer/stores/vaultExternalChanges.ts) + at least one in [vault.svelte.ts](src/renderer/stores/vault.svelte.ts) and the recovery flows.
- **Mechanism:** The "caller MUST cancel pending writes before calling applyReloadFromDisk" contract is unenforceable across 7+ call sites. It WAS missed in every site — that's why the audit found this as 3 separate criticals (6.0.C2, 6.0.C3) and 1 high ("CascadeDelete.undo / tagRewriteSweep / recreateDeletedFile bypass open-editor reload"). The pattern is the same shape, and any new caller of `applyReloadFromDisk` ships with the same hole.
- **Fix:** (a) Move `cancelMarkdownWritesForDocument(docId)` + `await flushAllPendingFrontmatterWrites()` for the docId **inside** `applyReloadFromDisk` itself, as the first action before `documentStore` state replacement. (b) Also hoist a `syncOpenEditorsAfterDiskMutation(paths, vaultRoot)` helper (currently inline in [replaceAllCommand.ts:214-222](src/renderer/commands/replaceAllCommand.ts:214) as `syncOpenEditors`) into a shared util and route `CascadeDeleteCommand.undo`, `tagRewriteSweep`, `recreateDeletedFile`, and any future disk-mutation-then-restore site through it. (c) Add a CI gate.
- **CI gate (new):** `scripts/check-reload-cancels-writes.mjs` — fail if any `.svelte`/`.ts` file *outside* `markdownFileWriter.ts` and `document.svelte.ts` calls `cancelMarkdownWritesForDocument` adjacent to `applyReloadFromDisk` (the manual pattern is now wrong). Also fail if `applyReloadFromDisk` is called without first being routed through the canonical helper.
- **Test:** unit — fixture with armed gateway timer + applyReloadFromDisk → assert cancel fired, no post-reload body lands. Plus a code-level test that `applyReloadFromDisk`'s first call is to `cancelMarkdownWritesForDocument`.

### 6.1.R2 — Vault-swap reset registry (class-kill: "X not cleared on vault swap") 🟠 ✅ 💾 M

- **Where:** All `.svelte.ts` stores; the existing `core/vaultLifecycle.ts` (`onVaultSwap`) registry. Today's leakers (today's audit): `inFlightDriftPrompts` ([vaultExternalChanges.ts:1257](src/renderer/stores/vaultExternalChanges.ts:1257)), `readOnlyTagToastShown` (fileTags.svelte.ts), `testFlushers` ([markdownFileWriter.ts](src/renderer/lib/vault/markdownFileWriter.ts)), `lastSeenArgs` (same), `uiStore.toasts` not firing onDismiss ([ui.svelte.ts:417](src/renderer/stores/ui.svelte.ts:417)), `lastWrittenConfigs` ([configWriteScheduler.ts](src/renderer/lib/boards/configWriteScheduler.ts)), `VaultFileItem.autoExpandTimer`, `KanbanSideToolbar.propDebounce`, `KanbanBoard.lastViewPersistTimer`. Likely more.
- **Mechanism:** The `onVaultSwap` registry exists but registration is *optional* and there's no enforcement that module-level mutable state is registered. Every store author has to remember; reviewers have to spot it. The CI gate `ci:vault-scoped-state` apparently doesn't catch Maps/Sets/setTimeout closures.
- **Fix:** (a) Replace each `onVaultSwap('pre-swap', name, fn)` with `vaultSwapResettable(name, fn)` — same signature, but the new helper *requires* a non-empty `fn` and registers a "name -> fn" pair the CI gate can inspect. (b) `uiStore`'s swap handler must iterate `toasts` and fire each `onDismiss?.()` before nulling the array (otherwise stranded promises wedge new-vault writes). (c) Extend the CI gate `ci:vault-scoped-state` to scan every `*.svelte.ts` for module-level `let`/`const Map`/`const Set`/`new Map()`/`new Set()`/`setTimeout(`/`setInterval(` and fail if the file doesn't ALSO call `vaultSwapResettable(...)` OR carry the inline escape `// allow-module-state: <reason>`.
- **CI gate (new/extended):** `scripts/check-vault-scoped-state.mjs` (extend existing). Inline escape token `// allow-module-state:` for genuinely-shared infrastructure (logger, registries) with a written reason.
- **Test:** unit — fixture per leaker that asserts the state is gone after `fireVaultSwap('pre-swap')`. One per Map/Set/timer.

### 6.1.R3 — `Command` base auto-dirties `targetBoardId` (class-kill: "command marks the wrong board") 🟠 ✅ 💾 S

- **Where:** [commands/Command.ts](src/renderer/commands/Command.ts), every concrete `Command` in `src/renderer/commands/`. Today's offenders: `UpdatePropertiesCommand` ([propertiesCommands.ts:148](src/renderer/commands/propertiesCommands.ts:148)), `UpdateOrphanFrontmatterCommand` ([kanbanCommands.ts:570](src/renderer/commands/kanbanCommands.ts:570)), the metadata-kind branch of `applySnapshot`. Audit2 2.4 already fixed `UpdateBoardSettingsCommand` — but as a one-off.
- **Mechanism:** Every command snapshots `this.targetBoardId` and the existing CI gate `ci:commands-target-board` enforces that field's presence — but the *use* of `targetBoardId` for `markDirty` is by convention. Commands routinely call `boardCacheStore.markDirty(boardStore.current?.id ?? '')` instead, which is wrong on cross-board undo (the `boardActivator` pivot is asynchronous). Some commands skip the `markDirty` entirely (metadata-kind branch).
- **Fix:** (a) Add `protected markBoardDirty(): void { boardCacheStore.markDirty(this.targetBoardId); }` to `Command.ts`. (b) Refactor `applySnapshot` / `applyOrphanPatch` / `applyFrontmatterPatchRebased` to accept `targetBoardId` as a parameter (no more reading `boardStore.current`). (c) Refactor each concrete command's `execute` / `undo` to call `this.markBoardDirty()` instead of `boardCacheStore.markDirty(...)`. (d) Add the CI gate.
- **CI gate (new):** `scripts/check-command-targets-self.mjs` — fail if any file in `src/renderer/commands/` references `boardStore.current` OR calls `boardCacheStore.markDirty(` with anything other than `this.targetBoardId`. Also fail if `boardStore.updateTile` / `boardStore.updateSettings` is called from a command file (commands should route through `boardCacheStore.persistUpdate*` with an explicit `boardId`).
- **Test:** unit — for each command (`UpdatePropertiesCommand`, `UpdateOrphanFrontmatterCommand`, `UpdateTaskFieldCommand`), assert: execute on board A, switch to board B, undo with A's `boardActivator` pending → board A is dirty, board B is not.

### 6.1.R4 — `renameAllPathKeys(oldRel, newRel)` chokepoint (class-kill: "X is stranded after rename") 🟠 ✅ 💾 M

- **Where:** [stores/vaultFolderOps.ts](src/renderer/stores/vaultFolderOps.ts) (`vaultFolderOps.rename`), [stores/vaultExternalChanges.ts:520-544](src/renderer/stores/vaultExternalChanges.ts:520) (`runExternalRenameCascade`), [stores/boardTiles.ts:203-221](src/renderer/stores/boardTiles.ts:203) (`renameTextTileBackingFile`). The relPath-keyed stores that today's audit identified as needing transfer: `markdownFileWriter.fileState`, `fileBaselineRegistry`, `inFlightDriftPrompts`, `markRecentSelfWrite` map, `readOnlyTagToastShown`, `vaultIndex` metadata, `boardCache` placements, `fileTags`, `documentStore.filename`. There are likely more.
- **Mechanism:** Today each rename cascade independently re-implements "update what I happen to remember." `markdownFileWriter.fileState` is the canonical missed example — every rename cascade forgets it, so post-rename body writes throw "refusing to write — not hydrated" on every keystroke. The cure isn't to teach each rename to remember more; it's to extract one function and forbid renames outside it.
- **Fix:** (a) Add `src/renderer/lib/vault/renamePathKeys.ts` exporting `renameAllPathKeys(oldRel: string, newRel: string)` which sweeps **every** relPath-keyed structure. Each store contributes its sweep via a registry (`registerPathRenamable(name, (oldRel, newRel) => void)`). (b) Each rename cascade calls `renameAllPathKeys(oldRel, newRel)` and nothing else. (c) Add the CI gate.
- **CI gate (new):** `scripts/check-relpath-keyed-stores-register-rename.mjs` — scan every `.svelte.ts` and `.ts` file for module-level `Map<string,` / `Record<string,` / `SvelteSet<string,` whose key looks like a relPath (heuristic: file matches keyed by literal `.md` /  any `relPath` named binding). Fail if the file doesn't ALSO call `registerPathRenamable(...)` OR carry `// allow-no-rename-transfer: <reason>`.
- **Test:** unit per registered sweep: fixture sets state for `Old.md`, fires `renameAllPathKeys('Old.md', 'New.md')`, asserts state for `Old.md` is gone and `New.md` carries the same value.

### 6.1.R5 — `hadBom` is sourced from disk reads only (class-kill: "BOM lost on first save") 🟠 ✅ 💾 S

- **Where:** [components/tiles/PropertiesPopup.svelte:213-217](src/renderer/components/tiles/PropertiesPopup.svelte:213) (the broken sniff), [lib/vault/markdownFileWriter.ts](src/renderer/lib/vault/markdownFileWriter.ts) (`readMarkdownForHydrate`, the canonical disk read), [components/tiles/TextTile.svelte:267](src/renderer/components/tiles/TextTile.svelte:267) (sibling-adoption path also vulnerable to inherited bad-BOM).
- **Mechanism:** `hadBom` is a property of the raw on-disk bytes. `vaultIndex.content` is already BOM-stripped by gray-matter, so `indexed.content.charCodeAt(0) === 0xfeff` is permanently `false`. Any caller that sniffs from in-memory content gets it wrong. PropertiesPopup is the surfaced bug; sibling adoption inherits it.
- **Fix:** (a) Mark `markHydrated(relPath, hadBom)` as **internal**; export only `markHydratedFromDisk(vaultRoot, relPath)` which calls `readMarkdownForHydrate` internally and is the only external entry point. (b) Refactor PropertiesPopup, TextTile sibling-adoption, and any other manual hydrate to use `markHydratedFromDisk`. (c) CI gate.
- **CI gate (new):** `scripts/check-no-bom-sniff.mjs` — fail if any `.svelte`/`.ts` outside `markdownFileWriter.ts` contains `charCodeAt(0) === 0xfeff` OR `\\ufeff` literal OR calls `markHydrated(` (the now-internal API).
- **Test:** unit — write a real BOM'd `.md` fixture, open via PropertiesPopup-only path (no TextTile mount), edit a property, assert the saved bytes still start with `0xEF 0xBB 0xBF`.

### 6.2.H1 — External `sync-frontmatter` leaves `originalFrontmatter` stale → comments dropped on next body-only save 🟠 ✅ 💾

- **Where:** [vaultExternalChanges.ts:163](src/renderer/stores/vaultExternalChanges.ts:163), [document.svelte.ts:275-279](src/renderer/stores/document.svelte.ts:275) (`setFrontmatter`), [document.svelte.ts:134-144](src/renderer/stores/document.svelte.ts:134) (`noteRawFrontmatter` else-branch), [frontmatterEngine.ts:75-79](src/renderer/lib/vault/frontmatterEngine.ts:75) (`patchFrontmatterSource`).
- **Mechanism:** `setFrontmatter(docId, next.frontmatter)` is called with **no** `rawFrontmatter` arg. `noteRawFrontmatter(docId, undefined)` clears the clean-bytes signal (rawFrontmatterCache) but the else-branch deliberately does NOT touch `originalFrontmatterCache`. Result post-sync: clean signal = gone, originalFrontmatter = stale. Next body-only save passes stale source into `patchFrontmatterSource`; the diff sees the external editor's value as different and rewrites the node, **losing its YAML comment**. The whole point of Audit2 4.8 is bypassed via the external-sync path.
- **Fix:** Re-parse `next.content` inline to extract `rawFrontmatter` and thread it through `setFrontmatter`. Alternative: propagate `rawFrontmatter` from `FileMetadata` (requires teaching `vaultIndex.parseMarkdown` to retain raw bytes — bigger blast radius, do only if `next.content` re-parse is too expensive).
- **Test:** fixture `.md` with a YAML comment, external editor flips a value, classifier returns `sync-frontmatter`, single keystroke fires body-only save → assert comment still present on disk.

### 6.2.H2 — Recovery sequencer Resume/Discard buttons fire-and-forget → concurrent recovery operations 🟠 ✅ 💾

- **Where:** [vault.svelte.ts:184-200](src/renderer/stores/vault.svelte.ts:184) (`awaitConfirm`), [vault.svelte.ts:607-627](src/renderer/stores/vault.svelte.ts:607) (tag-rewrite Resume), [vault.svelte.ts:656-683](src/renderer/stores/vault.svelte.ts:656) (rename-cascade Retry).
- **Mechanism:** `awaitConfirm`'s `onConfirm` runs `void convergeForward()` and resolves IMMEDIATELY (line 613). The next `await awaitConfirm(...)` in the sequencer fires while `renameTagEverywhere` is still pumping. Two recoveries now mutate `boardCacheStore.cache` and call `flushAllDirty` / `ensureAllLoaded` concurrently → wrong tile-defs flushed, sentinel cleared early.
- **Fix:** Restructure `awaitConfirm` so the handler's return is `await`ed before the outer promise resolves. The current closure form needs `onConfirm: async () => { await convergeForward(); }` AND `awaitConfirm` to thread that promise. Smallest surgical change: have `awaitConfirm` accept `onConfirm: () => Promise<void>` and `await` it before `resolve(true)`.
- **Test:** fixture vault with both sentinels present, sequencer plays through, assert second handler does NOT start until first's inner work resolves.

### 6.2.H3 — Recovery sequencer races `vaultIndexStore.rebuild()` — partial tag-rewrite misdetected 🟠 ✅

- **Where:** [vault.svelte.ts:454-516](src/renderer/stores/vault.svelte.ts:454) (`runPostCommitTasks` issues both `rebuild` and `runRecoverySequencer` as unawaited tasks), [tagRewriteSentinel.ts:258-269](src/renderer/lib/vault/tagRewriteSentinel.ts:258) (`hasPartialTagRewriteState` reads metadata).
- **Mechanism:** Both tasks are fire-and-forget. The sequencer's step 2 reads `vaultIndexStore.allMetadata()` while `rebuild` is still chunking the index. With no newName carrier yet, `partialDetected = false`, dialog shows "Discard plan", user clicks, breadcrumb cleared without convergeForward → vault left split.
- **Fix:** Either (a) await `vaultIndexStore.rebuild()` before running step 2, or (b) inside step 2, await `vaultIndexStore.isBuildingDone()` (add the helper) before reading metadata. (b) keeps the modal non-blocking on rebuild for the no-sentinel path.
- **Test:** fixture with mid-build index + tag-rewrite sentinel → assert step 2 sees the post-build metadata.

### 6.2.H4 — Quit handler exits on save failure with 200 ms toast window → silent data loss 🟠 ✅ 💾

- **Where:** [App.svelte:75-90](src/renderer/App.svelte:75) (`app:flush-and-quit`), [filenameUtils.ts:251-258](src/main/vault/filenameUtils.ts:251) (`atomicWriteFile` preserves tmp with `preservedTmpPath`), [tabsStore.close](src/renderer/stores/tabs.svelte.ts) (the right confirm pattern, for reference).
- **Mechanism:** Save throws → catch sets `failed=true` → 200 ms sleep → unconditional `app:ready-to-quit`. The user has ~200 ms to read a toast naming `<path>.<nonce>.tmp` before the window destroys. The recovery sentinel on next launch only names files, not tmp paths. `tabsStore.close` already has the right confirm flow; the quit path is asymmetric.
- **Fix:** Mirror `tabsStore.close`'s confirm flow. On `vaultStore.save()` returning false, `uiStore.openConfirm({title:'Save failed', confirmLabel:'Quit anyway', cancelLabel:'Stay open and retry'})`. On Cancel, signal main via new `app:cancel-quit` IPC that resets `isFlushingForQuit = false`. Also dump preservedTmpPath context into `.filo/quit-failure.json` so the next-launch recovery modal can surface locations.
- **Test:** mock `vaultStore.save` → false, fire `app:flush-and-quit`, assert confirm dialog opens, assert no `app:ready-to-quit` sent until user picks Quit-anyway.

### 6.2.H5 — `writeFrontmatter` empty-body fall-through when doc unloaded mid-debounce 🟠 ✅ 💾

- **Where:** [frontmatterWriteScheduler.ts:160-166](src/renderer/lib/boards/frontmatterWriteScheduler.ts:160), [frontmatterWriteScheduler.ts:174-185](src/renderer/lib/boards/frontmatterWriteScheduler.ts:174) (existing hydrate-then-write block).
- **Mechanism:** `body = docState?.body ?? vaultIndexStore.getMetadata(relPath)?.content ?? ''`. If `docState` is undefined at fire time, the `??` falls through. `vaultIndex.content` is the body-stripped, FM-stripped content from the last index parse (possibly hours stale). Final `?? ''` lands an **empty body** to disk.
- **Fix:** (a) When `docState` is undefined AND the writer was scheduled with a docId, **abort the write** (the editor vanished; preserve disk truth). (b) When `docState` is undefined AND docId is null, use the body returned by `readMarkdownForHydrate` (already paid for at L179) instead of vaultIndex.content. ### 6.2.H6 — Same-basename rename correlator pairs unrelated empty / identical files 🟠 ✅ 💾

- **Where:** [renameCorrelation.ts:85-106](src/main/services/renameCorrelation.ts:85) (`sameBasenameBytesPreserved`), [renameCorrelation.ts:188-201](src/main/services/renameCorrelation.ts:188) (same-basename branch).
- **Mechanism:** Refuses only on *positive* mismatch. Two empty files have size 0 and the same SHA-1 (`da39a3...`) → pair. Cross-basename pass has `CROSS_BASENAME_MIN_SIZE_BYTES = 256` floor; same-basename pass has no such guard. Synthetic rename emitted, tile refs silently rewritten.
- **Fix:** Add a same-basename guard: if both sizes are 0 OR both contents hash to the empty buffer SHA1, require parent-folder match OR refuse pairing entirely. Optionally apply a small-size floor (e.g. 32 bytes) to the same-basename pass too — any real document is bigger than that.
- **Test:** batch [delete A/Notes.md (hash X, empty), create B/Notes.md (hash X, empty)] → assert NOT correlated as a rename. Same with both files containing `# Title\n`.

### 6.2.H7 — `UpdateTaskFieldCommand` with `docId=null` is a silent no-op 🟠 ✅ 💾

- **Where:** [taskCommands.ts:333-420](src/renderer/commands/taskCommands.ts:333). Note: 6.1.R3 partially closes this (the wrong-board branch) but the docId=null silent no-op is a separate bug.
- **Mechanism:** Execute and undo both gate the patch application on `if (this.docId) documentStore.mergeFrontmatter(...)`. With null, the patch is never applied. The scheduler then writes the current frontmatter (no patch) back to disk. `markDirty` keeps the board scheduled but `.md` FM is untouched. Both legs no-op.
- **Fix:** (a) Reject `UpdateTaskFieldCommand` construction when `docId` is null (throw, like `DeleteFrameCommand` on a missing frame). (b) Migrate the docId-less path through the same orphan disk-write helper as `UpdateOrphanFrontmatterCommand` (after that command itself is rebased — see 6.2.H8 below).
- **Test:** fixture task with `docId: null`, push command, assert constructor throws OR the patch lands on disk.

### 6.2.H8 — `UpdateOrphanFrontmatterCommand` bypasses the rebase guard → external edits silently clobbered on undo 🟠 ✅ 💾

- **Where:** [kanbanCommands.ts:570-603](src/renderer/commands/kanbanCommands.ts:570) (`UpdateOrphanFrontmatterCommand`), [kanbanCommands.ts:717-790](src/renderer/commands/kanbanCommands.ts:717) (`applyOrphanPatch`), [history.svelte.ts:527-550](src/renderer/stores/history.svelte.ts:527) (`applyFrontmatterPatchRebased`, the right shape).
- **Mechanism:** `applyOrphanPatch` reads disk fresh (D.8), unconditionally spreads the patch, deletes empty keys, writes through the gateway. No per-field conflict detection. If the external editor changed the same field between execute and undo, the inverse patch blindly restores the pre-edit value.
- **Fix:** Add a docId-less variant of `applyFrontmatterPatchRebased(relPath, applying, expectedCurrent)`: read disk fresh, compare each `applying` key against `expectedCurrent`, only commit non-conflicting keys + prompt on conflicts. Route `applyOrphanPatch` through it. Audit2 4.2's helper has the right shape; this is "make it docId-less."
- **Test:** apply orphan FM edit, externally change same field, undo → assert external value preserved OR user prompted.

### 6.2.H9 — Reconcile loop is O(boards × tiles × markdown) — vault-open hang 🟠 ✅

- **Where:** [vault.svelte.ts:454-513](src/renderer/stores/vault.svelte.ts:454), [frontmatterSync.ts:257](src/renderer/lib/vault/frontmatterSync.ts:257) (`updatedAt = Date.now()` stamp), [boardCacheFrontmatter.ts:60-67](src/renderer/stores/boardCacheFrontmatter.ts:60) (`setCache({...cache})` identity churn per md file).
- **Mechanism:** The 5.3 fix walks `vaultIndexStore.allMetadata()` AND calls `applyFrontmatterToBackedTiles` per md, which itself reconciles every loaded board. For a 5k-file × 50-board × 100-tile vault: ~25M reactive cache mutations on every open. No chunking, no microtask yielding. The Svelte reactive graph thrashes; watcher events queue up.
- **Fix:** (a) **Drop the `updatedAt = Date.now()` stamp** in `frontmatterSync.ts` for reconcile-driven patches — it's not a user edit. (b) **Batch the cache identity flip:** mutate all changedBoardIds in a single pass, call `setCache({...cache})` ONCE at the end. (c) Chunk the outer loop: `await new Promise(r => queueMicrotask(r))` every 50 md files. (d) Skip files whose mtime is older than the board's `lastReconciledMtime` marker. (e) **Best:** drop the eager loop entirely — renders read frontmatter live; the cache is invisible at render time. The 5.3 fix's only consumer (a hypothetical downstream tool) is theoretical.
- **Test:** synthetic 1000-board × 100-tile fixture; assert vault open completes in < 200 ms wall clock; assert no `.board.json` rewrite when no FM actually changed.

### 6.2.H10 — `forceWriteForDocument` + `cancelMarkdownWritesForDocument` race in-flight writes 🟠 ✅ 💾

- **Where:** [markdownFileWriter.ts](src/renderer/lib/vault/markdownFileWriter.ts) — both helpers. The bug: a timer that fired-but-still-async-in-flight is not awaited by either.
- **Mechanism:** Cancel disarms the *timer* but a write whose `setTimeout` already fired is now in the `writeMarkdownFile` IPC await chain. A simultaneous `forceWriteForDocument` from a tab-close path arms a *second* write against the same path. Two writes race; the loser may overwrite the winner's bytes.
- **Fix:** Track in-flight writes per `(callerId, relPath)` in a `pendingWrites: Map<string, Promise<void>>`. `cancelMarkdownWritesForDocument` and `forceWriteForDocument` must `await` any existing pending entry for the same key before proceeding (cancel: wait for completion then drop; force: wait, then re-arm if state changed).
- **Test:** schedule write, advance timers to fire it (but don't resolve the IPC), call forceWriteForDocument concurrently, assert only one write reaches disk and the second observes the first's result.
